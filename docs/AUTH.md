# Вход и пользователи

Регистрации нет: людей создаёт администратор через внутренний порт сервера.

## Два порта сервера

    публичный   3004   /api/...       сайт и приложение
    внутренний  3006   /internal/...  только для локальной админки, наружу не публикуется

Внутренний порт защищён токеном (заголовок Authorization: Bearer ...), токен задаётся
в окружении (DVCLOUD_INTERNAL_TOKEN, не короче 32 символов). Сравнение за постоянное время.

## Публичный API

    POST /api/auth/login    {"login": "...", "password": "..."}  -> ставит куку, отдаёт человека
    GET  /api/auth/me                                            -> кто я (нужна кука)
    POST /api/auth/logout   {}                                   -> закрывает сессию
    GET  /api/health                                             -> состояние

Изменяющие запросы принимаются только как application/json: форма на чужом сайте так
отправить не может. Кука dvcloud_sid: HttpOnly, SameSite=Lax, Secure (кроме разработки).

## Внутренний API (для админки)

    GET   /internal/users
    POST  /internal/users                       {"login", "displayName", "password"?}
    PATCH /internal/users/:login                {"disabled"?, "quotaBytes"?}
    POST  /internal/users/:login/reset-password {"password"?}

Если пароль не передан, сервер придумывает его и возвращает один раз в ответе.
Хеш пароля наружу не отдаётся. Каждое действие пишется в таблицу audit_log
(без паролей и токенов).

## Защита

- Пароли: scrypt со случайной солью. Для несуществующего логина проверка всё равно
  выполняется, чтобы время ответа не выдавало, есть ли такой человек.
- Подбор: не больше 5 неудач на логин и 30 на адрес за 15 минут, потом ответ 429.
- Сессии: токен 32 случайных байта, в базе только его SHA-256. Простой 14 дней
  (настраивается), предел 90 дней. Отключение человека и смена пароля закрывают
  все его сессии.
- Ответы входа и /me не кэшируются.
