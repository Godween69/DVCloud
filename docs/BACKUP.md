# Резервная копия DV Cloud (0.9.0, переносной диск и журнал с 0.14.0)

Копия делается в админке, на вкладке «Копия», и только по кнопке. Сама по расписанию она не запускается.

## Что выбрать

На вкладке «Копия» вы сами отмечаете, что брать:

- **Фото и видео** и **База данных**: можно взять только файлы, только базу или всё. Для полного восстановления нужно и то и другое.
- **Точная копия** (папка `files`): файлы лежат так же, как в облаке. Из неё облако восстанавливается. Это основной вариант.
- **Копия по людям** (папка `people`): понятная раскладка для человека, чтобы открыть фото без облака. Для каждого человека своя папка, внутри подпапки по годам или по годам и месяцам (или без подпапок), имена как в облаке или с датой впереди (`2026-05-10_123000_IMG_1.jpg`: так файлы сортируются по времени съёмки даже в самой простой программе). Одинаковые имена получают « (2)». Можно добавить папку `albums`: для каждого альбома своя папка с его файлами. Файлы в такой копии настоящие, поэтому места она занимает столько же, сколько и точная. Можно включить обе копии сразу.
- Дополнительно для точной копии: брать ли то, что лежит в корзинах, и брать ли миниатюры и копии видео (их облако строит заново, обычно не копируют).
- Ограничение скорости для копии по сети.

Если вы позже поменяете раскладку или имена, прежние папки в копии остаются: старые файлы сами не стираются.

## Что копируется

- Папка **files** (точная копия): все фото и видео ровно так, как они лежат в облаке (`library` и `trash`). Миниатюры, превью и копии видео по умолчанию не копируются: облако строит их заново. Включить их в копию можно на той же вкладке.
- Папки **people** и **albums** (копия по людям): по желанию, см. выше.
- Папка **db**: выгрузка базы данных (люди, альбомы, группы людей, отметки, настройки). Это файл `dvcloud-ГГГГММДД-ЧЧММСС.dump`. Хранятся семь последних, старые стираются.
- Не копируются никогда: временные файлы (`tmp`, `uploads`) и ключ связи с удалённым сервером (`.backup-key`).

Удалённые вами файлы из копии сами не стираются: это страховка от случайного удаления. Если копия разрослась, её можно вручную почистить.

## Как это не мешает работе облака

- Копирование идёт в фоне с самым низким приоритетом процессора.
- Файлы в облаке записываются один раз и потом не меняются, поэтому копировать их можно, пока люди пользуются облаком.
- База выгружается одним согласованным снимком и при этом не блокируется.
- Для копии по сети можно задать ограничение скорости.
- Каждая следующая копия переносит только новое и изменённое, поэтому она быстрая.

После копирования автоматически выполняется проверка: файлы на месте назначения сверяются с облаком по размеру. Если за время копии люди успели загрузить новое, это показывается как «ещё не догнано», а не как ошибка: следующая копия заберёт их.

## Куда копировать

### Диск или папка

Подходит для USB-диска, второго диска в компьютере, сетевой папки (NAS, другой компьютер дома).

Облако видит одну папку внутри контейнера: `/backup` (переменная `DVCLOUD_BACKUP_DIR`). Нужно один раз подключить туда диск на самом сервере:

1. Подключите диск к серверу и смонтируйте его в обычную папку, например `/mnt/backup`. Для сетевой папки сначала смонтируйте её (SMB или NFS) на сервере.
2. Хозяином папки должен быть пользователь с номером 1000 (в контейнере это `node`):

        sudo chown 1000:1000 /mnt/backup

3. Добавьте серверу в `docker-compose.yml` примонтированную папку и перезапустите облако:

        services:
          server:
            volumes:
              - ./data:/data
              - /mnt/backup:/backup

4. В админке, на вкладке «Копия», выберите «Диск или папка», при желании укажите подпапку и нажмите «Проверить место».

Если диск отключён, облако не пишет «в никуда»: копия не запустится, а админка скажет, что диск не подключён.

### Другой сервер по SSH

Копия уходит на другой компьютер через SSH по ключу, пароль нигде не вводится.

1. На вкладке «Копия» выберите «Другой сервер по SSH», впишите адрес сервера, порт (обычно 22), пользователя и папку на сервере, нажмите «Выбрать этот способ».
2. После этого на странице появится **открытый ключ** облака. Это строка, начинающаяся с `ssh-ed25519`. Она не секрет.
3. Добавьте эту строку новой строкой в файл `~/.ssh/authorized_keys` пользователя на сервере назначения.
4. Нажмите «Проверить место». Если вход получился, будет написано, куда и сколько там свободно.

Закрытый ключ создаётся внутри облака (в каталоге данных, в `.backup-key`) и нигде не показывается. Первое подключение запоминает отпечаток сервера; если он потом поменяется, копирование остановится с ошибкой.

## Остановить копирование

Пока копия идёт, на вкладке «Копия» есть кнопка «Остановить копирование». Она прерывает передачу файлов или выгрузку базы
(на шаге раскладки читаемой копии остановка сработает, как только он закончится). Копия получает статус «ошибка: остановлено вами».
Уже скопированное остаётся на месте, следующая копия продолжит с этого места: rsync не копирует заново то, что уже есть.

## Копия на внешний диск скриптом

Если диск подключён не к серверу облака, а к другому компьютеру (например, к рабочему ПК с WSL), копию удобно сделать
скриптом `tools/backup-to-disk.sh`. Он задаёт вопросы по-русски, в админку заходить не нужно.

Запуск на компьютере, к которому подключён диск:

    bash ~/projects/DVCloud/tools/backup-to-disk.sh

Что происходит по шагам:

1. **Первый запуск.** Скрипт спрашивает адрес сервера облака для SSH и папку с данными облака на сервере.
   Ответы запоминаются в файле `~/.config/dvcloud/backup-to-disk.conf` (он только у вас и в репозиторий не попадает).
2. **Выбор диска.** Показывается список дисков с названием, файловой системой, размером и свободным местом.
   Диск C (системный) не предлагается. В WSL скрипт сам подключает нужную букву диска.
3. **Выбор папки.** Можно заходить в папки по номеру, подняться выше (`..`), создать новую (`+`) или выбрать текущую (`0`).
4. **Проверка.** Скрипт считает размер данных облака, сколько уже есть в копии и хватит ли места на диске.
   Затем показывает, откуда и куда будет копирование, и ждёт ответа «да».
5. **Выгрузка базы данных** в подпапку `db`, **копирование библиотеки и корзины** в подпапку `data`.
   Во время копирования видны полоса прогресса, проценты, скорость и оставшееся время с примерным часом окончания.
6. **Сверка.** После успешного копирования скрипт ещё раз сравнивает копию с источником и пишет, совпала ли она.

Ничего не удаляется ни на диске, ни на сервере. Остановить копирование можно в любой момент клавишами Ctrl-C:
уже скопированное остаётся, а следующий запуск с той же папкой продолжит с этого места.
Если в имени файла есть символы, запрещённые в Windows (двоеточие, вопросительный знак, звёздочка), такой файл
на диске NTFS не создастся: скрипт запишет это в файл `backup-errors-...txt` рядом с копией и покажет предупреждение.

## Переносной USB-диск (0.14.0)

Диск втыкается в USB сервера, подключается сам, а вся работа с копиями делается в админке, вкладка «Копия».
Выберите вид «Переносной USB-диск».

Что делает админка:

- Показывает карточку диска: подключён ли он, размер, сколько свободно, какая файловая система. Если диск вынули,
  не закрыв в Windows (NTFS помечен «грязным»), сервер его не подключит, и карточка подскажет выполнить в Windows проверку `chkdsk /f`.
- Сама создаёт папку копии с названием `Backup_DVCloud_ДД.ММ.ГГГГ` (дата подставляется сегодняшняя). Можно выбрать
  «продолжить последнюю копию» (допишет недостающее) или своё название папки.
- Перед запуском проверяет, влезет ли копия: размер всех файлов облака плюс запас 2 %. Не влезает: копия не стартует,
  админка пишет, сколько не хватает. Если папка уже частично заполнена, проверка пропускается: копируется только недостающее.
- Копирует файлы и выгрузку базы так же бережно к работе облака, как в остальных видах (под `nice`).
  На диски NTFS, FAT и exFAT права и владельцы не переносятся (флаги `--no-perms --no-owner --no-group`), это нормально.
- Ведёт журнал копий (таблица `backup_runs`): когда, куда, сколько файлов и байт, чем кончилась.
- Кнопки «Подключить диск» и «Безопасно извлечь». Извлечь можно, когда ничего не копируется; админка сначала сбрасывает
  записанное на диск и только потом говорит «можно вынимать».

Над копиями из журнала можно делать:

- «Проверить»: сверяет файлы копии с каталогом облака по размеру (для точной копии) и проверяет, что выгрузка базы читается.
- «Удалить…»: стирает папку копии с диска. Нужно ввести имя папки; без подтверждения ничего не удаляется. Облако не затрагивается.
- «Убрать запись»: появляется, если папку копии уже стёрли с диска руками; запись уходит из журнала.
- «Восстановить…»: на странице выбираются «Восстановить файлы» (возвращает недостающие файлы из копии в каталог облака; нужно ввести `ВОССТАНОВИТЬ`;
  существующие файлы не трогаются, а замена отличающихся включается отдельной галочкой) и «Восстановить базу».
  «Восстановить базу» возвращает базу из выгрузки копии. Нужно ввести `ВОССТАНОВИТЬ БАЗУ`. Перед этим рядом с копией
  автоматически кладётся страховочная выгрузка текущей базы (`before-restore-ДАТА.dump`). Копия должна быть сделана на той же
  версии структуры базы (номер миграции совпадает), иначе восстановление откажется. Журнал копий при восстановлении базы не затирается.

На вкладке «Копия» на каждом долгом и на каждом разрушающем действии есть кнопка «Остановить» или «Отмена».

### Как это настраивается на сервере

Облако в контейнере не может монтировать диски, поэтому на сервере нужны три вещи (при установке через compose из примера):

1. Правило udev и юнит монтирования, которые подключают диск по его UUID (`lsblk -f`) в папку, например `/mnt/usbbackup`.
   Для NTFS нужен драйвер ядра `ntfs3` (Linux 5.15 и новее), параметры `uid=1000,gid=1000`. В `/etc/fstab` ничего писать не надо:
   без диска сервер загружается как обычно. Пока диск не подключён, в этой пустой папке лежит файл-метка `.dvcloud-not-mounted`:
   подключённый диск закрывает её, так админка понимает, что диск на месте.
2. Папка, куда админка кладёт команды хосту (`cmd-mount`, `cmd-eject`), и юнит `.path`, который их выполняет и пишет ответ
   в `usb-result.json`. Контейнер сам ничего не монтирует и прав не получает.
3. Эти две папки в `docker-compose.yml`, причём диск с `propagation: rslave`, чтобы диск, воткнутый после запуска облака,
   появился внутри без перезапуска:

        services:
          server:
            environment:
              DVCLOUD_USB_DIR: /backup-usb
              DVCLOUD_CONTROL_DIR: /control
            volumes:
              - type: bind
                source: /mnt/usbbackup
                target: /backup-usb
                bind: { propagation: rslave, create_host_path: false }
              - type: bind
                source: /opt/docker/dvcloud/control
                target: /control
                bind: { create_host_path: false }

Пока `DVCLOUD_USB_DIR` пуст, вид «Переносной USB-диск» выключен. Без `DVCLOUD_CONTROL_DIR` кнопки «Подключить» и «Извлечь» не работают,
остальное работает с диском, смонтированным вручную.

## Как восстановить

Для копий на переносном диске восстановление есть в админке (см. выше). Ниже ручной способ для любой копии: он перезаписывает данные, поэтому делается осознанно.

1. Остановите облако (сервер и админку), но базу оставьте запущенной:

        docker compose stop server admin web

2. Верните файлы. Источник: `files/` из копии, назначение: каталог данных облака (`./data`). Если копия на диске:

        rsync -a /mnt/backup/dvcloud-backup/files/ ./data/

   Если на другом сервере:

        rsync -a пользователь@сервер:/путь/files/ ./data/

3. Верните базу из самой свежей выгрузки. Пустую базу создаёт сам Postgres при первом запуске; выгрузка накатывается поверх:

        docker compose exec -T db pg_restore --clean --if-exists --no-owner -U dvcloud -d dvcloud < /mnt/backup/dvcloud-backup/db/dvcloud-ГГГГММДД-ЧЧММСС.dump

4. Проверьте права: хозяин файлов должен быть пользователь 1000.

        sudo chown -R 1000:1000 ./data

5. Запустите облако. Миниатюры, превью и копии видео построятся заново сами.

Проверить, что выгрузка читается, можно в любой момент, не восстанавливая её:

    pg_restore --list dvcloud-ГГГГММДД-ЧЧММСС.dump

## Устройство

- `apps/server/src/files/backup.service.ts`: настройки (в таблице `settings`, ключи `backup` и `backup_last`), проверка места, запуск и ход.
- Внутренние пути `/internal/backup`: состояние, настройки, проверка, запуск. Админка вызывает их, сама ничего не копирует.
- В образ сервера добавлены `rsync`, `openssh-client` и `postgresql17-client` (клиент базы не должен быть старше самой базы).
- Адрес сервера, пользователь и путь проверяются жёстко (латиница, цифры и несколько знаков), чтобы из формы нельзя было подсунуть ключи команды.
- Журнал действий админа получает записи о смене настроек копии и о запуске. Пароли и ключи в журнал не попадают.
